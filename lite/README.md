# 轻量数据迁移归档工具 使用说明

## 一、这个工具做什么

把数据从一张表挪到同数据库的另一张表，让原表瘦下来。支持两种场景：

| 场景 | 模式名 | 适用情况 | 做法 |
|------|--------|---------|------|
| 整表归档 | `full_table` | 这张表**不再有新增数据**（比如历史日志表、已下线的业务表） | 改表名 + 建一张空表顶替原名，瞬间完成 |
| 条件迁移 | `conditional` | 表**还在用**，只把符合条件的老数据挪走（比如只搬一年前的订单） | 分批搬运 → 校验 → 按主键清单删源 |

两条路径都不改表结构、不跨库、不做字段变换。工具只搬数据，不做任何"智能"改写。

**核心原则**：删源数据只能依据"已经安全落到归档表、且校验通过的那批数据的主键"，绝不依据你写的筛选条件直接删。这是防误删的根基，下文详述。

抽样种子默认每次执行都不同，反复校验可扩大覆盖面；需要复现某次结果时用 `-seed` 指定种子，复查 SQL 头部会记录它。

## 二、四个动作

工具通过命令行参数 `-action` 选择动作，四者职责严格分开：

| 动作 | 做什么 | 删源数据吗 | 全表模式能用吗 |
|------|--------|-----------|---------------|
| `migrate` | 全表模式做改名归档；条件模式分批搬运数据到归档表 | **不删** | 能（全表模式只有这一个动作） |
| `verify` | 独立跑一遍全部校验（含随机抽样），输出报告 + 一份可手工执行的复查 SQL | **不删，只读** | 不适用（没搬数据，无需校验） |
| `sample` | 只做随机抽样逐字段比对，每次执行换一批行，可反复执行扩大抽查面 | **不删，只读** | 不适用 |
| `purge` | **先强制校验一遍**，全部通过才分批删源数据 | **删** | 不适用 |

`verify` 和 `purge` 用的是**同一套校验代码**（同一个函数），保证你人工核对时看的标准，和真正删除时卡的标准完全一致，不会出现"看的时候通过、删的时候换了套标准"。

全表模式遇到 `verify` / `sample` / `purge` 时，会**跳过这张表并打印提示**（不当作失败）。因为它只做改名，没有搬运和删除。一个配置里混着两类表时，可以放心用一条命令跑全部表，不用逐张 `-table` 挑。

### 2.2 危险操作的显式放行（`-force`）

两处默认会拒绝、必须显式加 `-force` 才继续的操作：

| 场景 | 默认行为 | 为什么 |
|------|---------|--------|
| 全表模式，源表带触发器或自己的外键 | 列出这些对象后拒绝改名 | `CREATE TABLE ... LIKE` 只复制列和索引，不复制触发器与外键定义。改名后它们留在归档表上，顶替原表名的新表没有：触发器逻辑不再执行，外键约束也不再拦孤儿数据 |
| `purge` 时抽样被关掉（`sample_rounds` 或 `sample_size` 为 0） | 拒绝删除并说明原因 | 抽样是发现"两行数据互换"的唯一手段，这种情况下记录数、求和、最值、分块计数会全部相等 |

`-force` 只影响这两处，其它预检（归档表已存在、别人引用这张表、临时空表残留）照旧直接拒绝，不给绕过的口子。


### 2.1 随机抽样种子与复现

抽样是概率性的，单次只能覆盖很小一部分行。`verify`、`sample`、`purge` 三者的抽样种子遵循同一套规则：

- **不指定 `-seed` 时**：每次执行自动取当前时间，必然抽到不同批次的行。反复执行 `verify` 或 `sample` 就能不断扩大抽查面，不会永远盯着同一批行。
- **候选集本身也随种子变化**：抽样的候选不是固定的一批行，而是"每个主键区间里离随机探针最近的那一条"，探针由种子生成。换种子就换一批候选，反复抽查才是真的换地方；早先按"每区间取第一条"的做法，候选集是固定的，换种子只是在同一批里换。

- **指定 `-seed 数字` 时**：抽到哪几行完全固定，用于复现上一次发现的问题。三个动作一开始就都会在日志里打印本次种子和对应的 `-seed` 参数；输出复查 SQL 时，文件头部也会标注。`purge` 校验成功不输出复查 SQL，靠日志开头那行留下种子记录。

```bash
dbmigration-lite -config config.yaml -action sample              # 每次换一批行
dbmigration-lite -config config.yaml -action sample -seed 4242   # 固定种子，可复现
dbmigration-lite -config config.yaml -action verify -seed 4242   # verify 同样支持复现
```

复查 SQL 文件：`verify`/`purge` 输出 `review_表名_时间.sql`，`sample` 输出 `sample_表名_seed种子_时间.sql`，后者带种子所以同一秒内反复执行也不会互相覆盖。

## 三、完整流程

### 3.1 全表模式（一条命令完成）

前提：这张表确认不再写入。

```bash
dbmigration-lite -config config.yaml -action migrate -table logs
```

执行四步：

1. **预检**（只读，发现任一情况立即停下）：
   - 归档表已经存在 → 报错，不覆盖；
   - 有外键或视图引用这张表 → 报错，避免改名牵连别的对象；
   - 本表带触发器、或本表自己引用了别的表 → 报错并列出这些对象，因为 `CREATE TABLE ... LIKE` 只复制列和索引，不复制触发器与外键定义，改名后它们会留在归档表上而新表没有。确认可以接受时加 `-force` 继续（见 2.2）；
   - 临时空表 `表名__new_empty` 残留 → 报错，要求先清理。
2. **建空表**：按源表结构复制一张临时空表（列、主键、索引、字符集一致；触发器与外键定义不在复制范围内，见上一条）。
3. **对齐自增值**：把空表的自增值设为 `max(源表主键最大值 + 1, 源表当前自增值)`。取两者较大值，是因为删过历史行时主键最大值会小于自增计数器，只按最大值 + 1 对齐会让新表重新发放已经用过的 id。源表没有整型单列主键时，这一步自动跳过并打印提示，不影响改名本身。
4. **原子改名**：一条 `RENAME TABLE` 语句把源表改成归档表、空表顶上原表名。这条语句是原子的——要么全成功，要么全不执行，业务无感知。


全程没有"搬运"和"删除"，只是换了个表名，天然不存在误删风险。

### 3.2 条件模式（三步，缺一不可）

前提：表还在用，只挪走符合条件的数据。

```bash
# 第一步：搬运（不删源）
dbmigration-lite -config config.yaml -action migrate -table orders

# 第二步：校验（只读，出报告 + 复查 SQL）
dbmigration-lite -config config.yaml -action verify -table orders

# 第三步：删除（内部再校验一遍，通过才删）
dbmigration-lite -config config.yaml -action purge -table orders
```

`-table` 参数可选，不写就处理配置里的全部表。

条件模式搬运时会实时显示进度，形如：

```
搬运进度: [======>                    ]   6%  896,188 / 13,057,038  用时 00:32
```

开头先打印本次命中的总行数和批大小，搬运过程中按百分比整数变化刷新同一行（用回车符覆盖，终端里看起来就是一条在走的进度条）。如果输出被重定向到日志文件，回车符不会覆盖，会按百分比留下约 100 行记录。断点续跑时会从上次累计的行数接着显示。搬运结束会强制显示 100% 并换行，再打印行数核对结果。

三步的关系：搬运完工具会提示你去做 `verify`；`purge` 内部强制再跑一次校验，你没法跳过。校验不通过，源表一行都不会少。

## 四、防误删的五道闸门

条件模式删数据前，有五道关卡层层锁定。**任何一道不通过，源表一根手指都不碰。**

| 闸门 | 做什么 | 挡住的风险 |
|------|--------|-----------|
| ① 归档表处理 | 全表模式：归档表已存在直接报错，不覆盖；条件模式：不存在则按源表结构创建，已存在则复用（为了中断续跑），但随后必过校验关 | 全表模式覆盖旧归档数据；条件模式即使复用了带旧数据的表，校验也对不上，删不掉源表 |
| ② 分批幂等搬运 | 按主键游标一小批一小批搬，写入用"主键重复就覆盖"的方式；每批完成记下断点 | 一次搬太慢、中途失败重头再来、重跑产生重复数据 |
| ③ 校验对齐 | 比对记录数、数值列求和/最值、主键分块计数、随机抽样逐字段 | 只比总数会被"总数相等但搬错行"骗过 |
| ④ 按主键清单删 | 只删"已校验通过的那批主键"，用主键值逐条删；**绝不按筛选条件删** | 搬运期间新落进条件范围的数据被误删 |
| ⑤ 数量守恒 | 每批删前核对"待删数 + 已删数 = 归档数"，删完查命中数必须为 0 | 删多、删少、删错 |

两条写死在工具里的红线：

- **不用清表命令**。哪怕全量搬完，也按主键分批删，不做 `TRUNCATE`——因为清表无法逐行校验，一旦前面逻辑有错，数据就全没了。
- **删除必须显式执行**。默认只搬不删，要删必须单独跑 `purge`。

## 五、校验项清单

`verify` 和 `purge` 跑的校验共五类：

| 类别 | 比对内容 | 作用 |
|------|---------|------|
| 记录数 | 源表满足条件的行数 vs 归档表行数 | 最基本的一致性 |
| 数值求和 | 每个数值列的 `SUM`，按类型决定精确或容差判定 | 抓金额类数据差异 |
| 数值最值 | 每个数值列的 `MIN` / `MAX` | 抓极端值差异 |
| 主键分块计数 | 把主键按区间切块，逐块比对两边行数 | 定位差异落在哪一段 |
| 随机抽样逐字段比对 | 抽中行按主键回读两张表的全部字段逐一比对 | 抓"两行数据互换"这类求和/计数发现不了的错误 |

抽样是概率性的，默认 3 轮 × 每轮 50 行 = 150 行。样本越大越可靠，理论上仍可能漏掉极个别错位，可以按需加大，也可以多跑几次 `verify` 或 `sample`——每次种子不同，相当于多次独立抽查（见 2.1）。

抽样采用主键分区随机探针：把归档表主键范围切成若干区间（数量是样本数的 3 倍，用来对抗主键空洞），每个区间先用种子生成一个随机探针点，再在库里取离探针最近的一条候选（向后找不到就向前回退），最后从候选里随机选出样本。探针由种子决定，所以换种子就换一批候选，反复执行才真正扩大抽查面。这样不会把全表主键读到程序里，几千万行的表也只返回几百行。当表很小或主键空洞极多、候选不足时，自动降级为逐行蓄水池抽样，保证小表也能抽满。

主键分块大小的默认值是 `block_size: 100000`，但分块**数量**另有上限 `block_count_max`（默认 1000）。主键是雪花 ID、时间戳这类跨度极大的值时，按固定块宽会切出天文数字个分块，工具会自动放大块宽把块数压回上限内并打印提示——此时差异定位精度变粗，但"通过/不通过"的结论不受影响。


## 六、数值比对规则

金额类数据最容易出问题的地方是精度，所以按字段真实类型分三种方式比对：

| 类别 | 涵盖类型 | 怎么接收 | 怎么比对 | 容差 |
|------|---------|---------|---------|------|
| 整数 | TINYINT / SMALLINT / MEDIUMINT / INT / BIGINT，含无符号 | 按字符串收，**绝不经过浮点数** | 转成整数精确比对 | 零，差 1 就失败 |
| 定点小数 | DECIMAL / NUMERIC | 按字符串收 | 按十进制精确比对 | 零，差最小位就失败 |
| 浮点 | FLOAT / DOUBLE | 转成浮点数 | 绝对 + 相对双阈值 | 可配置，见下 |

浮点判定公式：`两边差值的绝对值 ≤ 绝对容差 + 相对容差 × 两边绝对值中的较大者`。
默认：FLOAT 绝对容差 `0.0001`、相对容差 `0.00001`；DOUBLE 绝对容差 `0.000000001`、相对容差 `0.000000000001`。都可以在配置里改。

几个必须处理的细节：

- **精度不能丢**：无符号 BIGINT 最大值是 20 位数字，DECIMAL 可以做到 30 位小数，都远超浮点数的 15 位有效数字。所以整数和定点小数从头到尾用字符串和精确数值对象比对，不让浮点数插一脚。
- **定点小数写法差异**：`1.0` 和 `1.00` 数值相等，比对前先规范化再比。
- **NULL 严格区分**：NULL、0、空字符串三者互不相同。求和时全为 NULL 的结果是 NULL，不是 0。

## 七、复查 SQL

`verify` 跑完，除了控制台报告，还会生成一份 SQL 文件，**同一份内容既写文件也原样打印到控制台**，两处完全一致。你可以直接贴到数据库客户端跑，亲自核对。

复查 SQL **按字段类型分别生成**，不会所有金额字段都套同一句模板：

- **整数 / 定点小数**：列出两边 `SUM`，注明"零容差，必须完全相等，差 1 即失败"；
- **浮点**：除两边 `SUM`，额外生成一句可直接运行的容差判定 SQL，返回 1 表示在范围内；
- **金额字段**：附带 `COUNT(字段)` 显示非空数量，防止字段全是 NULL 时把 NULL 误看成 0；
- **抽样部分**：列出抽中的主键清单，以及回读两张表对应行逐字段比对的 SQL。

输出文件位于配置里的 `output.dir` 目录，命名格式 `review_表名_时间戳.sql`。

## 八、配置文件逐项说明

完整示例见同目录 `config.example.yaml`。各字段含义：

### 顶层

| 字段 | 含义 | 默认值 |
|------|------|--------|
| `database.dsn` | 数据库连接串，格式 `用户名:密码@tcp(地址:端口)/库名?parseTime=true` | 必填 |
| `database.max_open_conns` | 最大同时打开的数据库连接数 | 10 |
| `database.max_idle_conns` | 保持空闲的连接数 | 5 |
| `output.dir` | 复查 SQL、报告输出目录 | `./migration-output` |
| `checkpoint.dir` | 断点进度文件目录 | `./migration-checkpoints` |
| `tables` | 要处理的表列表，一个配置文件可以同时管多张表 | 至少一张 |

### 每张表

| 字段 | 含义 | 默认值 |
|------|------|--------|
| `name` | 源表名 | 必填 |
| `mode` | `full_table`（整表归档）或 `conditional`（条件迁移） | 必填 |
| `archive_table` | 归档表名 | 必填 |
| `condition` | 条件模式的筛选条件（就是 SQL 的 WHERE 部分）；全表模式不允许配置 | 条件模式必填 |
| `key_column` | 主键列名；留空则自动探测。条件模式（搬运、校验、按主键删）要求单列整数主键；全表模式只做改名，探测不到整型主键时跳过自增值对齐，仍可执行，但配了与表实际主键不一致的值会直接报错 | 留空 |
| `batch_size` | 每批搬运的行数 | 5000 |

### 校验相关（`verify` 子节点）

| 字段 | 含义 | 默认值 |
|------|------|--------|
| `numeric_fields` | 需要做数值校验的列名，类型自动探测 | 空 |
| `block_size` | 主键分块大小，用于定位差异落在哪一段 | 100000 |
| `block_count_max` | 分块数量上限。超过时自动放大 `block_size`，防止大跨度主键切出过多分块 | 1000 |
| `abs_tolerance` | 浮点绝对容差，整数与定点小数始终零容差 | 0.0001 |
| `rel_tolerance` | 浮点相对容差 | 0.00001 |
| `sample_rounds` | 抽样轮数，设为 0 关闭抽样 | 3 |
| `sample_size` | 每轮抽样条数，总样本数 = 轮数 × 每轮条数 | 50 |

## 九、断点续跑

条件模式搬运时，每批完成都会把进度写到断点文件，命名 `cp_表名.json`，内容包含配置指纹、已完成的最后一批最大主键、已搬行数。

- 中途中断，重新跑 `migrate` 会从断点继续，不重复、不遗漏；
- 配置指纹用于防止配置被改后误续旧进度：条件、批大小、校验字段、抽样参数任一变化，指纹就变，工具会拒绝续跑并要求你确认；
- 进度文件写入用"先写临时文件再改名"的方式，避免中途断电留下半截文件。

删除动作也支持续跑：每删完一批，就把删除进度写进同一个进度文件（删到哪个主键、累计删了多少行）。中途中断后重新执行 `purge`，工具会读出上次删到哪里，**只校验还没删的那部分数据**，然后从断点继续删，不会重复删、也不会从头再来。全部删完后进度标记为"已完成"，再跑会直接跳过；如需重做，删掉进度文件即可。

需要知道一个边界：删除和写进度**不在同一个事务里**。如果进程恰好在一批删除已提交、进度还没落盘时被杀，重跑会发现源表少了这一批、归档表没少，两侧行数对不上而拒绝删除。方向是安全的（绝不会误删），但会卡住，此时按提示核对后删掉进度文件重跑即可。


删除开始前和结束后各检查一次"有没有新数据落进归档范围"，发现就停下并提示重新搬运、重新校验。这是为了补回计数方式优化后原本由"每批重新统计总数"顺带提供的提醒。另外每批删除都会核对"计划删多少、实际删多少"，数量对不上立即停止，不带着错误继续往下删。

## 十、使用注意事项

1. **条件列必须是不随时间变化的列**（比如创建时间），不要用会被修改的列（比如更新时间）筛选。否则搬运窗口内数据被改，校验会报差异、工具停下——这正是设计意图：带着疑问绝不删。
2. **表要能正常 UPDATE/DELETE**：删源是按主键逐条删，需要业务避开大规模写入窗口；工具不做实时变更捕获。
3. **归档表在同一数据库**：跨库、跨实例不在本工具范围内。
4. **先拿非核心表试跑**：建议完整走一遍 `migrate → verify → purge`，确认复查 SQL 你能看懂、数据对得上，再用于核心表。
5. **全表模式确认不再写入**：改名是瞬间的，如果还有业务往原表名写数据，改名后数据会写进新空表——这本身是安全的，但要确保那不是你想要的归档数据。
